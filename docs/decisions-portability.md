# 跨宿主兼容决策记录（portability）

> 状态：讨论中（2026-11-10）。只记录已确认的结论与理由，未定的放最后。

## D1 不再为每个宿主单独做插件

- **结论**：不新增「WorkBuddy 插件」「豆包插件」。核心能力（档案、经验、报告、教学状态机）先作为 DSH 插件内部模块收敛边界，**暂不拆成独立进程/MCP 服务**；等第二个宿主被真实用户触发后，再抽 `lab-mcp` 薄壳。
- **理由**：真正有价值的是实验档案、经验库、报告引擎、教学状态机，这些与宿主无关；但 5 小时/周不足以同时维护独立服务 + 多宿主。先保证模块边界干净，抽离成本可控。

## D2 目标是「体验一致」，但通过外挂 UI 实现

- **结论**：桌宠、气泡、面板、高亮框继续作为独立 WinForms 窗口存在，不嵌入宿主页面；宿主只负责唤起和传上下文。
- **理由**：现有 UI 已经是 OS 级独立窗口（TopMost + TransparencyKey），本身可复用；面板的数据请求走 `Program.ApiBase`（`overlay/LabPet.cs:1798`），只要把这份 HTTP API 抽成独立服务，面板不需要改。

## D3 目标是公开项目，优先级 WorkBuddy > 豆包

- **结论**：先接 WorkBuddy（MCP + Skill），豆包只做连通性验证。
- **理由**：WorkBuddy 的 MCP/Skill 接入成本最低；豆包的自定义连接器要求「服务器 URL + Headers」，本地 `127.0.0.1` 是否可用未知，且公网化会引入数据出境问题。

## D4 接受一次重构

- **结论**：在外部用户仍为 0 时完成 core 拆分，不等有人用了再拆。
- **理由**：当前 GitHub 2 star / 0 fork / 最新 release 6 次下载，重构窗口最好。

## D5 放弃豆包工作适配

- **结论**：不做豆包连接器，也不做公网 relay。
- **理由**：豆包自定义连接器要求公网可达的服务器 URL；公网化与「数据只留本机」冲突，且域名/服务器/稳定性都是持续成本。收益（多一个入口）远小于代价。

## D6 UI 随宿主插件分发，不做独立安装包

- **结论**：桌宠与面板继续打包在宿主插件里，用户不额外安装桌面程序。
- **理由**：少一个安装步骤；但该选择与「维护 ≤5 小时/周」和「本校课程使用」存在冲突，见待定问题。

## D7 数据只留本机

- **结论**：实验档案、截图、老师模板默认不离开本机；不做云端同步、不做公网中转。
- **理由**：公开项目里这是最容易翻车的地方；也直接否决了豆包方案。

## D8 维护上限 5 小时/周，同时只维护一个宿主适配

- **结论**：在第一个宿主没有真实学生用户之前，不启动第二个宿主的适配。
- **理由**：两个宿主 × 安装/文档/issue 已超过 5 小时/周；先让一个宿主跑通真实课程。

## D9 成功标准：本校课程真实使用

- **结论**：三个月内以「同班/同课程同学能独立装好并完成一次实验」为成功，不以 star 数为目标。
- **理由**：公开仓库先作为交付物，不作为社区运营目标。

## D10 第一版只服务一门课 + 1~2 个软件

- **结论**：范围锁定一门实验课（候选：计算机网络 / eNSP），不追求多课程覆盖。
- **理由**：5 小时/周只够把一门课的经验库、报告模板、故障样本打磨到「真的省时间」。

## D11 宿主分阶段：先 DSH，WorkBuddy 设触发条件

- **结论**：第一版继续以 DSH 插件交付（已跑通、安装路径已验证）；WorkBuddy 适配在「≥3 个真实 WorkBuddy 用户明确要求」后再启动。
- **理由**：两个宿主 = 两套安装文档 + 两套 issue，超过维护上限；先把一门课跑通，比多一个入口更能验证价值。
- **状态**：待 Q12 确认同学实际使用的宿主后锁定。

## D12 成功标准具体化为「3 个同学独立完成一次实验」

- **结论**：三个月内，3 名同班同学在只读文档的情况下，独立装好并完成一次实验、生成一份报告。
- **理由**：比 star / 下载量更能证明插件有价值，也直接检验安装路径是否真的可行。

## D13 宿主锁定 DSH

- **结论**：第一版只做 DSH，WorkBuddy 在触发条件满足前不动。
- **理由**：已跑通、安装路径已验证、日常在用；5 小时/周只能维护一个入口。

## D14 课程锁定「计算机网络 + eNSP」

- **结论**：经验库、报告模板、故障样本只围绕这门课和 eNSP 打磨。
- **理由**：环境兼容坑最多，最能体现只读探测与经验库的价值。

## D15 验证方式：干净 DSH_HOME 先行，真 VM 待补

- **结论**：已在全新 `DSH_HOME` 下完成插件安装、配置合成、启动、API 与桌宠首次编译验证；真 Windows VM 因官方 ISO 下载仅 ~30KB/s（5.4GB 约 50 小时）暂缓。
  - **2026-11-11 更正**：30KB/s 是某个链接/时段的个例，已作废。官方静态 CDN 实测单连接 1.14 MB/s、4 并发 1.12 MB/s（沙箱出口代理锁总带宽），5.4 GB 约 82 分钟。真 VM 不再因速度排除，见 `plan-remaining-verification.md` 的 P4b。
- **结果**：插件 0.15.6 被 DSH 正确识别，`/dsh-lab/api/status` 正常，`LabPet.exe` 首次编译并运行。
- **待补**：真干净系统、eNSP 只读探测、150% DPI、杀软拦截。
- **新发现（0.15.7 已修）**：`assetStatus()` 仍判断 `swim.png`（实际为 `swim_1..8`）；插件包包含预编译 `overlay/LabPet.exe`，已从 `files` 排除。干净 profile 复测：`states` 全 true，`frames` swim 8 / dash 3。

## D16 本版不抽 MCP，只做 core 门面

- **结论**：新建 `lib/core.mjs`，收敛 **22 个宿主无关方法**（原计划 12 个，T1 盘点后修正），`index.js` 退化为 DSH 适配层；暂不引入独立进程或 MCP 服务。
- **理由**：33 个工具里没有任何执行体直接依赖 DSH API，抽离成本比预想低；未来加 MCP 只需套协议壳。
- **结果（0.15.8）**：`lib/core.mjs` 已承载 22 个方法；`index.js` 1670 → 1191 行；工具与面板报告接口统一走 core；35 个测试 + 3 自检全绿；干净 profile 端到端生成 docx 通过。
