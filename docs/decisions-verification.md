# 验证策略决策记录

> 记录「怎么验证软件目录里的软件」这件事的决定，与 [decisions-portability.md](decisions-portability.md)（宿主移植）分开。
> 每一条包含：结论、理由、以及它约束了什么。

---

## D1 每轮验 3 个，重质量而非数量

- **结论**：每轮验证固定 3 个软件，每个都写完整记录（来源、SHA-256、命令、断言、可复现性、局限）。
- **理由**：验证的价值在于「断言设计得对不对」，不在于数量。堆 10 个"能启动"等于没验。
- **约束**：3 个要覆盖不同的软件形态，避免全是同一类。第一轮（SWMM/EPANET）验的是**命令行求解器**；本轮覆盖**脚本语言**、**便携批处理**、**GUI + 批处理**。

## D2 允许安装到隔离目录，不再强求零安装

- **结论**：允许运行安装程序，但必须装到 `D:\lab-verify\<软件>`，验完必须卸载并逐项核对残留（目录 / 注册表 / 服务 / 计划任务 / 开始菜单 / 进程）。
- **理由**：真实学生就是装。上一轮只验免安装包，等于永远绕开最痛的安装环节——而"装完打不开"恰恰是学生最常遇到的问题。
- **约束**：安装前记快照，安装后 diff；卸载后再核对一次。**能解包就不装**（解包优先，但不能因此完全不验安装路径）。

## D3 GUI 也要验：只验"指路 + 截图"，不验点击

- **结论**：每个软件都要验 `desktop_guide`（高亮框 + 气泡）和 `desktop_screenshot`（真实截窗）；`desktop_click` 不验。
- **理由**：`guided` 模式下代码层面就禁止代点，验了也没有实际意义；而"能不能正确框住控件、能不能截到窗口"才是真实风险点——学生看到的是黄框，不是命令输出。
- **约束**：GUI 验证需要真实桌面会话（桌宠进程 + 窗口句柄），不能在没有交互桌面时做。

## D4 校验命令写进 catalog，schemaVersion 升到 2

- **结论**：`coursepacks/software-catalog.json` 增加 `verify` 字段（`cmd` / `expect` / `timeoutMs` / `tolerance` / `note`），`schemaVersion` 从 1 升到 2。
- **理由**：只写在文档里，知识会散落，下次还得人肉重写；写进 catalog 才能被教学循环直接消费。
- **约束**：加字段必须同时补「读取侧兼容」（旧条目没有 `verify` 时要能正常返回）和「结构校验」（测试要卡住字段类型），不能只改 JSON。

## D5 验证完全删，不保留软件

- **结论**：验证结束删除整个 `D:\lab-verify`，包括下载包、解包/安装的软件、测试模型和输出。
- **理由**：要的是"验证记录"而不是"装一堆软件"。记录里有下载地址 + SHA-256，随时可复现。
- **约束**：删除必须用文件系统复核（`ls` / `Test-Path`），不能只看退出码——本机曾出现"报错但实际已删"的情况。

## D6 `verified-run` 不要求结果可复现，但必须单独标注

- **结论**：跑通一次最小实验即可提升为 `verified-run`；是否"两次结果一致"作为 `verify.deterministic` 字段单独记录，不写进状态门槛。
- **理由**：GUI 类软件（LTspice、JASP）本身不保证逐字节可复现，硬卡会让它们永远升不上去；而"结果确定性"对教学循环是否适用 `verifyCmd` 又非常关键，所以必须显式记录。
- **约束**：不确定的软件要在 `notes` 里写清"不能用作自动判分"，避免被误用。

## 待定问题

1. **安装路径的残留边界**：注册表项算不算"污染"？如果装完能卸干净但会留空键，是否可接受？
2. **GUI 验证的判定标准**：截图"有内容"太松，"框正好框住目标"太严。需要一个可操作的中间标准（例如：截图非纯色 + 目标区域与原图差异超过阈值）。
3. **多版本共存**：同一软件装两个版本时，`verified-run` 记录要不要区分版本号？（目前是在 notes 里写版本，没有结构化字段）
4. **谁来跑验证**：现在是本机人工触发。要不要做成 `scripts/verify-all.mjs` 一键跑全部已登记 `verify` 的条目？

## 本轮执行清单（3 个）

| 软件 | 形态 | 版本 | 下载 | 验证方式 | 结果 |
| --- | --- | --- | --- | --- | --- |
| R | 脚本语言 / 统计 | 4.6.2 | `mirrors.aliyun.com/CRAN` | `Rscript -e` 数值断言 | ✅ `verified-run` |
| Blender | 便携批处理 / 三维 | 4.5.0 LTS | `mirrors.tuna.tsinghua.edu.cn/blender` | `blender -b -P` 渲染 + 读像素 | ✅ `verified-run` |

**已排除**：QGIS（官网安装包版本无法稳定定位，1GB+）、JASP（1.2GB，且无 CLI）、eNSP/Wireshark（需装 Npcap 驱动）、Packet Tracer（需 NetAcad 账号）。

### 执行后的补充结论

1. **D2 的价值被证实**：LTspice 的 MSI 忽略 `INSTALLDIR`（真实属性是 `TARGETDIR`，且被固定指向 AppData）。如果只验解包版，就发现不了这个安装语义差异；而学生机器上"装完不知道装哪去了"正是这类问题。
2. **D3 超额完成**：GUI 验证不但跑通，还顺带查出 LTspice 批处理失败的根因（首启对话框）。**GUI 验证不只是"截图好看"，它能解释 CLI 层的异常。**
3. **D4 的代价比预估小**：加 `verify` 字段只改了生成器的一处判断和两条测试断言，没有波及业务代码。
4. **D6 需要收紧一点**：Blender 属于「像素确定但字节不确定」，`deterministic: true` 必须配 `note` 说明比对方式，否则会被误用成文件哈希比对。

## D7 后续验证按难度分层推进，而不是按优先级

- **结论**：新增 [VERIFICATION_DIFFICULTY_RANKING.md](VERIFICATION_DIFFICULTY_RANKING.md)，把 131 个未验证条目按「验证成本」分成 T1~T5，后续按档位成批推进。**不再按 P0/P1/P2 的优先级排序。**
- **理由**：优先级反映的是「教学重要性」，不是「验证成本」。同一批里既有 20 分钟的 Git，也有 6 小时的 SOLIDWORKS；按优先级推会把最贵的最先做，一次批次就可能耗掉整个周末。
- **判定规则**（脚本 `scripts/rank-verify-difficulty.mjs` 固化）：
  - 机器分 = CLI 可判定性 + 授权门槛 + 平台可得性 + 优先级 + 体积/依赖
  - **两条硬规则覆盖机器分**：许可拿不到（需院校授权 / 需订阅 / 需厂商授权）→ 最低 T3；包体过大 → 最低 T3
  - 31 条人工修正，逐条写明理由（如 Wireshark 有 CLI 但装 Npcap 驱动 → T4）
- **新增维度「授权可得性」**：比难度更硬的约束。131 个里 **60 个需院校授权**，没有校园许可就等于验不了，这不是难度问题。
- **约束**：分层只决定「先验谁」，不改变 `verified-run` 的判定标准（仍是跑通一次最小实验 + 写清局限）。

## D8 T3~T5 不做全量验证，改「抽检 + 按需复现」

- **结论**：
  1. **T1 / T2 全做**（共 31 个），因为它们能产出 `verify`（可自动判分的断言）
  2. **T3 / T4 只做抽检**：每档挑 1~2 个**能代表一整类**的软件，结论标注为「同类外推」
  3. **T5 永久不做**，保持 `catalog-only`
  4. **按需复现**：谁卡住了就针对谁做一次，比预先全验省一个数量级
- **理由（不是时间问题）**：
  - **边际信息量递减**。已验证的 9 个已经覆盖了全部验证形态：CLI 求解器（SWMM/EPANET）、脚本语言（R）、便携渲染（Blender）、GUI + 批处理（LTspice）、数据库（MySQL）、图像处理（ImageJ）、机器学习 GUI（Weka）、便携解释器（Python）。「能不能启动、能不能被定位、能不能截图」已在 3 个异构软件上 3/3 通过，再验 18 个 T3 得到的是同一结论的重复，不是新知识。
  - **一半条目根本借不到许可**。131 个里 66 个需院校授权 / 订阅 / 厂商授权（T3 有 29 个、T4 有 34 个）。这不是排期能解决的。
  - **T3/T4 的产出多是 `verified-diagnose`**（能启动 + 能截图），进不了 `verify`。而教学循环真正消费的是 `verify`。
- **约束**：
  - 抽检结论**必须**写成「同类外推，非逐项验证」，不得表述为"这一类都验过"
  - `catalog-only` 本身是诚实状态，不影响查询、识别、兼容建议；"没验"不等于"没用"
- **例外（任一满足即可破例）**：
  1. 用户 / 同学**实际要用**（例如 eNSP，虽属 T4，但是本项目核心场景）
  2. 有**免费教育授权 + 具备 CLI 或批处理**（例如 AutoCAD 的 `accoreconsole` 被低估）
  3. 它能**代表一整类**，抽检有外推价值
- **资源去向**：省下的时间投到「经验沉淀」而不是「再多验几个」——见 D9。

## D9 经验闭环：采集自动化 + 注入前置 + 三张数据表合并

- **结论**：按 [plan-knowledge-loop.md](plan-knowledge-loop.md) 实施经验闭环，核心是三件事：
  1. **采集自动化**：`guide` / `click` / `screenshot` / `record_result` 成功后由代码自动落盘，**不再依赖 agent 调 `note_add`**
  2. **注入前置**：经验塞进 `experiment_get`（agent 开工必读）和 `desktop_guide`（每次指路必调）的返回里，而不是只写进事后才看的 `handoff.md`
  3. **三表合并**：把 `page-maps`（控件名）、`guide-presets`（历史坐标）、`notes.where`（文本）合成一张 `interface/<software>.json`，查询优先级：同版本 UIA 实时 > 同版本历史坐标 > 跨版本（标 `versionDrift`）> 文本
- **理由**：
  - 现状已核实——`report_generate` 确实会自动读经验并写进 `handoff.md`，但**报告正文不读**，**实验开始时也不读**；`workflow` 第 2 步只是一句文字提示，agent 跳过就完全失效。
  - 三套数据互不识别：preset 只有坐标没控件名，page-map 有控件名不记历史坐标，`where` 是自由文本不可执行。**不合并就等于每次都要重新量一遍。**
- **约束**：
  - L2 只录**指引**，不录点击回放（`guided` 禁止代点的硬约束不能破）
  - L5 报告片段只给句式骨架，**不得携带数值**，产出不得标"已核对"
  - 注入硬限流（坑 5 / 控件 8 / 失败 3），防止上下文膨胀
  - 采集可在面板一键关闭；锚点图只裁控件周边；全部只存本机
- **验收**：不看"功能上线"，看指标——首次指引命中率 ≥70%、量坐标次数下降 ≥50%、`pending` 章节数下降、失败不重复。
  - ⚠️ **0.15.15 修订**：其中「`pending` 章节数下降」经三轮实测证伪（见 D10），已替换为「片段候选覆盖 / 片段不含数值 / 不得标已核对」。其余指标保留。
- **顺序**：批次 1（L1 + 注入）单独就能解决"经验事前不可用"，价值最高；L3 视觉锚点排最后，做不出来也不影响闭环。

## D10 经验闭环实施完成：五个批次全做，方案按证据修订

- **结论**：0.15.15 一次性完成批次 1~5（L1 控件库 + 经验前置 + `usedSource` 埋点 / L2 自动录制 + L6 热区 / L4 失败反例 / L5 报告片段 / L3 视觉锚点），不停下等确认；所有需要用户拍板的事集中在最终清单里。
- **实施形态**：一个库（`lib/knowledge.mjs`）+ 两个零依赖模块（`lib/png.mjs`、`lib/anchor.mjs`）+ 三处注入（`experiment_create/get`、`desktop_guide`、`handoff`/`report_generate`）。没有另起六套实现。
- **验证**（每批次跑过多遍）：
  - 全量单测 **60+**、自检 **3/3**、pack-check 通过；新增 `test/knowledge.test.mjs`、`test/knowledge-host.test.mjs`、`test/anchor.test.mjs`
  - 合成基准 `scripts/benchmark-knowledge.mjs`：13 个控件，第一次命中 0 / 需量坐标 13 次；第二次命中 12（可靠 10、降级 2）→ 命中率 **92.3%**、可靠命中率 **76.9%**、量坐标下降 **92.3%**；`usedSource` 四种状态齐全
  - PNG 解码覆盖 filter 0~4 与 RGBA；锚点覆盖平移、1.25 倍缩放、空白图/低纹理/坏数据的降级
- **按「反复检验确认有错」修订了方案**（证据写在 [plan-knowledge-loop.md](plan-knowledge-loop.md) 第九节）：
  1. `software`/`controlName` 参数**本来就有**，方案写"新增"是错的
  2. 合并 page-maps **只能用 `rel`（相对整窗）**，用 `rect`（屏幕绝对）会整体框偏
  3. `page_map_guide` 必须一并改走 interface，否则留第二套查询路径
  4. 「报告 pending 下降」三轮实测 `3→3→3` 且 `generateReport()` 不接收 knowledge，指标无效 → 换成可测的片段/命中率指标
- **实施中补上的坑**：C# `/guide` 命中 UIA 时 `x/y` 基准会变成控件矩形（用历史坐标必须清 `control`）、旧 preset 键兼容、中文文件名碰撞、`interface-live` 未真正命中时诚实降级、自动采集与用户主动写入的边界。
- **约束保持**：不代点、不跨用户共享、不上传、片段不携带数值、报告正文不写经验、`guided` 模式硬约束不变。
- **偏差（需用户确认）**：C# 面板开关未做（改由工具/设置 API）、归档压缩未做、L3 只做合成图验证未做真实 GUI 端到端、追问次数与失败重复率需真人两次实验。
- **隐私说明**：[knowledge-data.md](knowledge-data.md) 写清采集内容、存放位置、关闭方式与删除方法（手动删目录是彻底删除，不进回收站）。

## D11 第一轮确认：先搞懂再做，八条逐条定案

- **来源**：0.15.15 交付后用户对 8 项确认的逐条回复，详见 [confirmations-2026-11-10.md](confirmations-2026-11-10.md)（含每条的代码证据、"有什么用"的解释、代价与依赖）。
- **本轮约束**：用户要求「先回答和记录，全搞懂之后再做」→ 只解释与记录，**不改代码、不 bump、不重新打包、不发版**；0.15.15 包保持有效。
- **定案**：
  1. **不做全量真人实验**：取消预先安排，改为 **case-driven** —— 用户后续反馈真实使用问题时再针对性复现。「追问次数下降」「失败重复率」明确标注**暂无数据、不作承诺**，不得写成已验收。
  2. **报告片段不主动套用**：用户判断「agent 写正文就很可以了」成立。片段只进 `handoff.md` 与 `report_generate` 返回值，不进正文、禁带数值、不得标已核对；**维持现状，第 5 项否决**。
  3. **锚点触发策略保持不变**：只在 `usedSource` 为 `none` / `preset-window` 且存过锚点时才兜底，理由是误框比降级更坏；是否调整**必须等真实 GUI 实测数据**。
  4. **不推送**：GitHub 远程仍未配置，发版与推送等用户明确指令，不得自作主张。
- **已批准待开工**：① L3 真实 GUI 端到端验证；② 归档压缩 `actions` 摘要 + 片段按 `课程 + 软件` 细分；③ C# 面板开关与热区展示（问清用途后待定，建议与 ① 合并成一次编译验证）。
- **两条依赖**：真实 GUI 验证 → 锚点策略调整（靠数据）与面板改动（同一次桌宠编译）；第 5 条 → 片段按软件细分**只是检索精度改动，不得被误读成放宽使用边界**。
- **自动采集默认开（已定案）**：用户第二轮明确「需要做」→ **保持默认开启**，并升级为产品约束：**不得静默改成默认关**，如需更改必须单独决策并同步改隐私说明。它是闭环唯一输入，关掉则 `interface/` 恒空、L1 命中率归零；代码 `store.mjs:11` 已实现、已有测试钉住默认值（`knowledge-host.test.mjs:138,209`），本轮只记录、不改代码。配套「面板可见开关」仍随第 1 项待定。
- **更正（第二轮）**：D11 初稿与 `confirmations` 初稿把热区描述成「助教看到全班卡点」，**与 D10「不跨用户共享」硬约束自相矛盾**。热区只由本机 `noteGuideOutcome`（`bumpUsage`）与 `rebuildUsage`（扫本机 `actions/*.jsonl`）生成，**看不到别人的经验库**；跨用户汇总违反方案第七节隐私红线，当前架构也没有这条路。第 1 项面板热区展示的价值相应从「看全班」降级为「看自己」。详见 [confirmations-2026-11-10.md](confirmations-2026-11-10.md) 文末。

- **第三轮核实（20:08）：第 1 项两个东西都没有用处，建议删除待办 C**。用户质疑「agent 能默认查看不就行了」，用四层核实（静态代码 / 真实调用 / 反向扫描 / 回归）证明确实如此：
