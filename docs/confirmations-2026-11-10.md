### 1. C# 面板补「自动采集」开关 + 热区展示 —— 问「做了有什么用」

**现状（代码证据）**

- 面板全部 `Api("GET"...)` 只有 `/status`、`/experiments`、`/report/templates`（`:1471,1476,1629`），**没有任何经验/热区/采集状态端点**。
- 但卡片里**没有** `autoCapture` 复选框；总开关目前只能由 agent 调 `lab_knowledge_settings(off/on)`（`index.js:1129`）或直接 PUT 设置 API（`index.js:1404`）来改。
- 热区数据已经在算：`usage/<软件>.json`（`knowledge.mjs:460,472`），`knowledgeFor()` 会把高频项注入返回（`:585`），但**面板上不显示**。
- 默认开：`store.mjs:11` `autoCapture: true`，`knowledge.mjs:128` 读它。

**做了有什么用**（⚠️ **2026-11-10 第三轮：以下两条价值判断已作废**，见文末「第三轮核实」。保留原文只为可追溯，**不要再据此决策**。）

### 4. 自动采集默认开启 —— 问「这个有什么用」

### 5. 报告片段要不要更主动地套用骨架 —— 问「这个有什么用，按理来说 agent 写正文就很可以了」

**用户判断是对的，这一项不该再往前推。**

**现在的实现**：`report_fragment_add(course, section, pattern)` 存句式骨架；`report_generate` 用 `fragmentHints(exp.course, 章节名)` 取候选（`core.mjs:486`），只放进 `handoff.md`（`:535`）和返回值 `fragmentHints`（`:552`）。**报告正文一行都不进**，硬规则是「禁止携带数值、产出不得标已核对」。

**理论上有什么用**：只解决**术语/句式一致性**——同一门课第二次写「分析」章节时，agent 不用重新发明学科套路；换模型、换会话、换 agent 时报告调性更稳。**不提升事实正确性。**

**为什么不值得更主动**：

- 报告质量的瓶颈是「有没有真实测量值、分析有没有依据」，不是「句式像不像」。片段解决不了瓶颈。
- 项目硬规则是「加速但不编造」。方案第九节自己就写了「L5 会抄自己」：复用上次分析文字而本次数据不同，会写出看似合理实则错误的结论。**主动套用等于把这个风险放大。**
- agent 本来就要按本次实测值重写正文，骨架反而多一层需要核对的东西。

**结论**：**维持现状**——片段只是 `handoff` 里的改写参考，不主动套用、不进正文。**第 5 项确认不做。**

**与第 7 项的关系（潜在的矛盾，先写清）**：第 7 项「L5 片段按软件细分」是**检索精度**改动（让候选按 `课程 + 软件` 索引，别串到别的软件），**不是**放宽使用边界。所以两件事不冲突：按软件细分照做，"保持不主动套用"不变。若后续有人把"按软件细分"误读成"可以自动填进正文"，以本条为准。

### 6. 锚点触发策略放宽 / 收紧 —— 问「具体用处」

**当前策略（代码证据 `index.js:665`）**：只有当 `usedSource === 'none'` 或 `'preset-window'`（即控件级定位、历史坐标**都没**可靠命中，只落到窗口级或完全没命中）时，才调 `anchorLocate()`；且 `anchorLocate` 内部还要求该控件**存过锚点**（`:198` `if (!item || !item.anchor) return null`）；匹配不到一律降级整窗高亮。

**具体用在什么场景**：**eNSP / Qt / 自绘 UI 这类 UIA 读不到控件名的软件**。此时 `interface/` 里没有控件条目、preset 只到窗口级，锚点是唯一还能指到"某一个按钮"的手段。UIA 能读到控件时，实时定位本来就比模板匹配准，不该让模板抢。

**为什么这么保守（三个真实代价）**：

1. 每次匹配要多截一张图 + 全图多尺度扫描，纯 JS 实现，有可感知耗时；
2. 锚点图会随 DPI / 主题 / 窗口缩放失效，**误匹配比不匹配更坏**——框错位置会直接把学生指到错的按钮；
3. 降级路径的成本很低（退回整窗高亮 + 一句提示），没必要为了"尽量命中"去赌误框。

**放宽会怎样**：每次指路都先跑匹配 → 更慢、误框率上升，且会抢掉本来更准的 UIA 实时定位。
**收紧会怎样**：只在人工存过锚点时才用 → eNSP 这类基本用不上，L3 等于白做。

**结论**：**保持现状**，不凭感觉调。第 2 项真实 GUI 验证会给出耗时、命中率、误命中率的实测数字，**拿到数据再决定是否调整**。

**状态**：解释完毕，策略不变；**依赖第 2 项**。

## 第三轮核实（2026-11-10 20:08）：第 1 项的两个东西到底有什么用

**用户质疑**：「那 1 的面板开关打开有什么用，agent 能默认查看不就行了，热区的经验库同理，你现在多次检查并确认第一项的两个东西具体有什么用，不要再脑补了」。

**核实方式（四层，全部可复跑）**

| 层 | 做了什么 |
| --- | --- |
| ① 静态代码 | 读 `core.mjs` 三处 `knowledgeFor` 注入的**实际返回字段**、`knowledgeQuery` / `knowledgeSettings` 实现、`settings` API、C# 设置卡片与 `SavePet()` 全文 |
| ② 真实调用 | `temp/verify-round3.mjs`：临时 homeDir 造 3 条热区（导出 6 成 / 启动 3 败 / 保存 1 成）+ 1 条坑，依次调 `experiment_create`、`experiment_get`、`knowledge_query`、`knowledge_settings(status/off/on)`、`report_generate`；结果落 `temp/verify-round3-result.json`，跑完自动删临时档案 |
| ③ 反向扫描 | `hot` / `autoCapture` / `usageFor` / `dataInventory` 的**全部**读取点；C# 全部 `Api("GET"...)`；确认没有面板专属数据通路 |
| ④ 回归 | 63 单测 + 3 自检全绿；`knowledge.test.mjs:212` 已有热区断言，`:225,275` 已有 autoCapture 断言 |

**探测脚本自身的两次纠错**（避免误报成产品 bug）：`reportGenerate` 是 **async**，漏 `await` 时返回 Promise、`Object.keys` 为空，一度误以为 handoff 生成失败；加 `await` 后正常（608 字，含「已知经验 / 界面地图 / 坑」）。另外返回的 `handoff` 是**文件路径**不是正文，正则必须读文件内容。两处都是探测写错，**不是产品缺陷**。

### A. 面板开关（`autoCapture` 复选框）

| 问题 | 结论（依据） |
| --- | --- |
| 现在有吗 | **没有**。卡片只有称呼 / 大小 / 显示 / 待机动画 / 自由走动（`LabPet.cs:1333-1360`）；`SavePet()` 只 PUT `/settings` 的 `dataDir`，面板**从不 GET `/settings`**，连开关当前值都不知道 |
| agent **默认**看得到开关状态吗 | **不能**。`experiment_create.knowledge` 只有一句 brief（`core.mjs:183` limits 全设为 0）；`experiment_get.knowledge` 的 8 个字段里没有 `autoCapture`（实测第 4 项 `false`） |
| agent 能拿到吗 | 能，但要**主动**调 `knowledge_settings(status)` → `autoCapture` + 六个目录文件数（实测第 7/8 项）；HTTP `GET /settings` 同样返回（第 10 项） |
| agent 能改吗 | 能。`knowledge_settings(off/on)` 实测 `false → true`（第 9 项）；HTTP `PUT /settings` 也行 |
| 面板能做到 agent 做不到的事吗 | **不能**。同一个 `store.updateSettings()`、同一个字段 |
| 真要做，改什么 | 不是「加个复选框」：要新增 `GET /settings` 回填当前值、复选框状态、`PUT` 带 `autoCapture`、并处理与 `Program.Config`（另一套配置）的关系 |

**唯一剩下的差别（推理，不是代码事实）**：面板是常驻进程，不依赖 agent 会话；agent 路径必须先有在跑的会话。这是**入口差别**，不是功能差别。前两轮给的「可控性 / 可解释性 / 隐私」属于把入口差别当功能价值讲，站不住。

**结论**：对「通过 agent 使用插件」的场景，**没有用处**。只有用户明确要「不开会话也能关采集」时才成立——那是产品偏好。

### B. 面板热区展示

| 问题 | 结论（依据） |
| --- | --- |
| 数据从哪来 | `usage/<软件>.json`，唯一生产点 `knowledge.mjs:585` `usageFor()`（默认 top 5） |
| agent **默认**看得到吗 | **看得到，且不用主动调**。`experiment_get` 返回的 `knowledge.hot` 是完整条目（实测第 3 项：3 条，各含 `key / hits / ok / fail / lastAt`） |
| 想看更多 | `knowledge_query(hot: 50)` 可放宽（实测第 6 项）；`KNOWLEDGE_LIMITS.hot = 5` 只是 `experiment_get` 的默认限流 |
| agent 有看不到的地方吗 | `handoff.md` 不含热区（实测第 11 项 `false`），但那是报告交接单，放热区本来就不对 |
| 面板现在有吗 | **没有**。C# 全部 GET 只有 `/status`、`/experiments`、`/report/templates`，没有任何经验/热区端点 |
| 面板能显示 agent 拿不到的东西吗 | **不能**。同一份 `usageFor()` 结果 |

**结论**：**没有用处**。面板展示 = 把 agent 在 `experiment_get` 里已经默认拿到的同一份数据再画一遍，不新增信息。用户判断成立。

### 总结论

第 1 项的两个东西**都不新增信息、不新增能力**，只是把 agent 已有的数据 / 操作换一个入口。前两轮我连续两次给它找价值（「助教看全班」→「使用者看自己」），都是在脑补；用实测把话说死后，价值归零。

### A：L3 真实 GUI 端到端验证 → 发现并修掉 4 个真缺陷

**验证前旧算法在真实图上的表现（这是合成图测不出来的）**：

| 现象 | 旧结果 | 根因 |
| --- | --- | --- |
| 窗口平移后 | 误报命中 `(1202,168)`，期望 `(225,113)`，score 0.902 | 打分 `1 - 平均绝对差/255` 分母固定 255，不与模板/图块能量挂钩；重复工具栏纹理拿到虚高分 |
| 纯色空白窗口 | **没有降级** | 同上：平坦区域去均值后差异小，被当成「很像」 |
| 主题反色 | 误报 score 0.892 | 同上 |
| 窗口改尺寸后 | 误报 `(453,25)` score 0.917 | 同上 + 尺度范围含 0.8，精搜缩到 0.776 倍 |

**修复（`lib/anchor.mjs`）**：

1. 打分改为**归一化互相关 NCC**（积分图同时存 ΣI / ΣI²，O(1) 取候选方差），并要求候选图块方差 ≥ 模板方差的 12% → 纯色/反色必降级。
2. 尺度集从 `[0.8,...,1.5]` 收窄为 `[0.9,1,1.1,1.25,1.5]`（真实 DPI 没有小于 0.9 的场景）。
3. 粗搜从「只留 1 个最佳」改为**保留 6 个互不靠近的候选，逐个精搜，精搜 NCC 定胜负**；粗搜门槛降到 0.3（只负责提名，不负责判定）。真实 GUI 实测正确位置在粗搜常排第 2。
4. 精搜从「只试粗搜估计尺度 ±3%」改为**枚举完整尺度集**（粗搜会把 1:1 模板估成 1.1，旧逻辑里根本没有 1.0，自匹配 NCC 掉到 0.58）。
5. 精搜后做**双峰歧义检测**：两处相距足够远的候选分数差 < 0.03 → 降级（指错比不指更坏）。
6. 新增 `diagnose:true` 选项，降级时返回 `reason` 与粗/精搜中间值，便于以后排查；**正常调用仍严格返回 `null`**，宿主照旧降级为整窗高亮。
