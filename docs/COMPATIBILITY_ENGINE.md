# 配置适配引擎

## 目标

实验助手不是“把所有软件都装一遍”，而是回答下面这类问题：

> 这台电脑现在是什么配置、已经装了什么版本、课程要求什么版本、当前实验能不能跑；如果可以跑，就不要乱改；如果跑不了，应该换哪个版本、按什么顺序装、哪些冲突要先处理、失败后怎么恢复？

因此，插件需要三层知识，而不是一份软件名单：

1. **软件目录**：知道某门课可能用到什么软件；
2. **配置适配档案**：知道某软件在哪些系统/依赖组合下可用；
3. **真实验证记录**：知道某套组合是否在目标机器上真正通过最小测试。

当前完成的是第 1 层全学科索引，以及第 2 层的首批样板。第 3 层已完成 eNSP 只读检测，以及 Python 3.12.10、Weka 3.8.7、MySQL 8.0.46、ImageJ 1.54f 的单机最小实验；`0.2.1` 增加“失败驱动换版本”与**本机经验库**，但只有 eNSP 建立了失败特征表，其余软件仍走“先采集、不猜版本”。

## 决策流程

```text
用户说明课程和实验目标
→ 读取指导书/课程要求
→ 只读采集电脑环境
→ 识别已安装软件及版本
→ 判断当前环境是否已经可用
→ 可用：保留，不为了“最新版”折腾
→ 不可用：匹配兼容档案
→ 展示候选方案、安装顺序、冲突、风险和回退
→ 用户确认
→ 安装或指导安装
→ 最小运行测试
→ 成功则记录为本机已验证
→ 失败则保存诊断证据，不反复重装
```

关键原则：

- **能跑就不要乱动。** 用户当前能完成实验的环境优先保留。
- **推荐不等于授权。** 引擎只能给出方案，安装、卸载和修改系统设置必须单独确认。
- **版本组合优先于单个版本。** eNSP 的关键不是“eNSP 最新版”，而是 eNSP、VirtualBox、WinPcap/Npcap、Wireshark、Windows 虚拟化状态之间的组合。
- **课程要求优先于社区经验。** 老师要求 VirtualBox 5.2.44 时，不能因为 7.x 更新就推荐升级。
- **社区方案必须标注可信度。** “网上很多人说可以”不等于本机已验证。
- **检测不到不等于没装。** 网页版、绿色版、服务器版和自定义目录都可能漏检，必须允许手工补充。

## 环境指纹

首批采集：

- Windows 版本、架构、内存；
- CPU 虚拟化固件状态；
- Hyper-V / 虚拟化安全是否运行；
- eNSP、VirtualBox、WinPcap/Npcap、Wireshark 的安装名与版本；
- 用户当前是否能完成实验（必须由用户回答，不能猜）。

后续增加：

- 显卡与驱动版本；
- 磁盘剩余空间和安装路径；
- 电脑是否加入校园许可网络；
- 软件实际启动路径与进程；
- 课程指导书要求的版本；
- 错误码、日志和最小拓扑验证结果。

## eNSP 样板

首批配置档案包含三种策略：

### 1. 当前可用：保留

如果用户明确表示 eNSP 现在能完成实验：

- 不推荐卸载 VirtualBox；
- 不因为版本较新就要求降级；
- 记录当前实际版本组合和最小拓扑结果；
- 只有出现新故障时才重新诊断。

### 2. 已安装但不确定：先诊断

如果检测到 eNSP 和 VirtualBox 6.x/7.x，但不知道是否能跑：

- 先采集启动错误和虚拟网卡状态；
- 不直接卸载较新 VirtualBox；
- 先做最小拓扑；
- 确认失败原因后再选择更换版本。

### 3. 新装或已确认失败：候选经典组合

社区资料大量指向 eNSP `V100R003C00SPC100`、VirtualBox `5.2.44`、WinPcap `4.1.3` 和兼容的 Wireshark 3.x，但需要注意：

- 这不是华为当前官方支持矩阵，eNSP 传统版早已停止更新；
- Windows 11 的 Hyper-V/VBS、驱动和权限会改变结果；
- Wireshark 与 Npcap/WinPcap 的安装顺序和兼容选项存在不同经验；
- 必须先备份、记录现有版本并做最小运行测试；
- 不能把社区经验直接标为“官方推荐”。

该候选档案保存在 `coursepacks/compatibility-profiles.json`，状态为 `community-reported`，不会被当作已验证事实。

## 推荐结果应该包含什么

不是一句“安装 5.2.44”，而是完整决策包：

- 为什么选这个方案；
- 适用和不适用条件；
- 组件精确版本；
- 安装顺序；
- 需要关闭/避开的冲突项；
- 高风险动作确认；
- 最小运行测试；
- 失败诊断方法；
- 回退路径；
- 方案来源与可信度。


## 失败驱动换版本（0.2.1）

用户说“装完还是跑不了”时，不能重新推一套方案了事。流程是：

```text
报错原文
→ 匹配失败特征（签名）
→ 命中：可能原因 + 先核对项 + 候选版本（按证据排序）
→ 未命中：不猜版本，先采集版本号、错误码、系统 build
→ 试一个版本 → 记一次结果（可用 / 失败）
→ 下次生成方案时自动调整顺序
```

### 证据分级

候选版本不是按“版本号新旧”排序，而是按证据强度：

| 证据 | 基础分 | 含义 |
|---|---|---|
| 本机经验库已记录可用 | 100 + 15 | 这台机器上真的跑通过 |
| 本机实测可用 | 100 | 系统 build 与验证记录一致 |
| 他机实测通过 | 68 | 在别的机器上跑通，当前系统不同，需复测 |
| 厂商文档 | 62 | 官方支持矩阵或文档 |
| 社区经验（未验证） | 40 | 网上说法，未经本项目验证 |
| 待验证 | 20 | 只是候选 |

调整项：

- 这台机器上试过且失败：-130，直接沉底；
- 与当前正在报错的版本相同：-70（若该版本在本机验证过，只 -20，并提示“先查环境变化”）；
- 本机记录过可用：+15，并把标签改成“本机经验库已记录可用”。

**关键点：** `proven-this-machine` 只有在“系统 build 对得上”或“本机经验库有记录”时才算本机证据。换一台 Windows 10 的电脑，同一个版本会自动降为“他机实测”，不会冒充保证可用。

### 本机经验库

记录文件：

```text
$DSH_HOME/lab-assistant/repair-history.json
```

每条记录包含：软件、组件、名称、版本、结果、系统指纹、报错原文、时间。同一组合重复记录只累计次数，不重复堆条目。数据只在本机，不上传。

### 适用边界

- 目前只有 eNSP 有失败特征表（设备启动失败、抓包/网卡异常、主程序打不开）；
- 其他软件命中不了特征时，只输出采集清单，不会凭空编造版本号；
- 引擎不下载、不安装、不卸载；所有换版本动作由用户确认后手动执行；
- 候选版本里的“社区经验”永远标注未验证，即使它排在第一。

对应实现：`lib/remedy.mjs`、`coursepacks/compatibility-profiles.json` 的 `failurePlaybook`，测试见 `test/remedy.test.mjs`。

## 新增软件的门槛

把 `catalog-only` 提升为 `verified-diagnose`，至少需要：

1. 一个真实安装样本；
2. 版本和依赖采集脚本；
3. 一次实际启动；
4. 不修改系统的失败路径；
5. 测试能证明“装没装、什么版本、能不能启动”。

提升为 `verified-run`，还需要：

1. 一个课程实验的最小操作闭环；
2. 真实截图/输出；
3. 异常分支；
4. 重启后可恢复；
5. 用户确认结果有效。

## 与其他 Agent 的关系

配置适配层属于共享核心，DSH、WorkBuddy 和未来宿主都调用同一套环境指纹与方案库。宿主适配器只负责把推荐展示给用户、发起确认和调用安装器，不各自维护互相矛盾的版本知识。
