# 后续验证计划（0.15.16 之后）

> 这份文档回答一个问题：**接下来还验什么、按什么顺序验、什么算验完了、什么永远不验。**
> 与 [VERIFICATION_DIFFICULTY_RANKING.md](VERIFICATION_DIFFICULTY_RANKING.md) 的分工：那份回答「谁难谁易」，这份回答「谁先谁后、怎么算过」。

状态词统一用这五个，别混：

| 状态 | 含义 | 能不能对外说"支持" |
| --- | --- | --- |
| `已验` | 有命令、有断言、有证据文件 | 能，但必须带局限说明 |
| `进行中` | 装了、在跑，还没出结论 | 不能 |
| `未开工` | 排了批次但没动 | 不能，仍是 `catalog-only` |
| `被挡` | 缺许可 / 缺驱动 / 缺硬件，客观做不了 | 不能，写明缺什么 |
| `不排期` | 决定不投入 | 不能，保持 `catalog-only` |

## 二、三条线，不要混在一起做

| 线 | 回答的问题 | 产出 | 会不会改 catalog |
| --- | --- | --- | --- |
| **软件线** | 某个软件能不能支撑一次实验 | `support` 升级 + `verify` 字段 | 会 |
| **平台线** | 同一功能换个系统状态还准不准 | 能力边界说明 + 回归测试 | 不会 |
| **使用线** | 真人用的时候卡在哪 | 复现步骤 + 修复 + 回归 | 可能 |

混着做的坏处：软件线一批 3 个，平台线一次要改系统设置，使用线得等人反馈。节奏完全不同，排在一起会互相堵。

### 3.3 每批的固定流程（八步，不许省）

1. **前置核查**：授权是否拿得到、包体多大、要不要驱动/许可服务器/虚拟化。拿不到许可就记 `被挡` 并写明缺什么，**不要硬装**。
2. **隔离安装**：装到 `D:\lab-verify\<软件>`，不写系统目录、不改 PATH。能便携就便携，能解压就不安装。
3. **只读诊断**：版本、安装路径、界面技术栈（Win32 / WinForms / Qt / Java / Electron）。这一步决定后面能不能用 UIA。
4. **最小实验**：自己写最小输入，跑一次，**先算理论值再比对**。不许拿软件输出当期望值——那等于用它证明它自己。
5. **二次运行**：同输入跑两遍，数值逐项比对。浮点比较给容差，文件哈希只在确定无元数据时用（Blender 的 PNG 就是反例：像素一致、字节不同）。
6. **GUI 能力**（仅 GUI 类）：UIA 控件树数量、窗口定位、`PrintWindow` 截图、必要时存一个锚点试匹配。
7. **清理**：卸载 → 删目录 → 核查注册表/服务/驱动残留（用 Python `winreg`，本机 `reg.exe` 被安全策略挡）。清理不彻底就如实写，别假装干净。
8. **归档**：catalog 升 `support` + 写 `verify` 字段 → 更新 `VERIFICATION_2026-10-28.md` → CHANGELOG → bump 版本 → 重打包。**没归档等于没验。**

### 3.4 判定规则

| 情况 | 判定 | 写进 catalog 的字段 |
| --- | --- | --- |
| 有 CLI/批处理 + 数值断言 + 两遍一致 | `verified-run` | `cmd`、`expect`、`timeoutMs`、`deterministic`、`note` |
| 只能启动 + 定位窗口 + 截图 | `verified-diagnose` | `note` 写明"只能证明装得上、认得出" |
| 装不上 / 许可拿不到 | 保持 `catalog-only` | `note` 写明缺什么、什么条件下可重试 |
| 断言过了但结果不可复现 | `verified-run` + 明确标 `deterministic: false` | D6：不要求可复现，但必须单独标注 |

**红线**：断言写错会把好软件判成有问题。LTspice 那次就把"末端 5V"写错了（脉冲 5ms 已落回 0），又把 5τ 的 99.33% 当成 100%。**先算理论值，再写断言。**

### 3.5 证据要求

一批做完，至少留下这四类：

- **命令与完整输出**（含退出码），不是"跑通了"三个字
- **产物文件**（`.raw` / `.rpt` / `.png` / `.log`），存在实验目录里
- **截图**（GUI 类必须有，且是真实 `PrintWindow`，不是自己画的）
- **清理结果**（哪些进程还在、哪些注册表键还在）

不算证据的：目测正常、软件自己报"success"、截图里只有桌面没有目标窗口。

### P1 · 运行中改缩放（100% ↔ 125% ↔ 150%）

- **现象**：Windows 设置里改"缩放与布局"，已存的锚点小图是按旧 DPI 截的，同一控件在新 DPI 下像素尺寸变了。
- **现在的代码怎么处理**：锚点多尺度搜索，尺度集 `[0.9, 1, 1.1, 1.25, 1.5]`，命中不了就降级整窗高亮。
- **没验的部分**：改完缩放**不重启**桌宠，直接再用。WinForms 在 PerMonitorV2 下不会自动重排布局，桌宠大小/位置可能不对；已存锚点可能全部失效。
- **具体怎么测**：先存一个 Notepad 按钮锚点 → 改缩放 → 不重启桌宠，直接 `anchor_locate` + `desktop_guide` → 记命中坐标与真实坐标的偏差 → 改回原值再测一次。
- **通过标准**：4 种切换方向 × 3 个控件，**0 次指错**；降级必须带 `diagnose` 原因。允许"降级"，不允许"指到别处"。
- **失败后果**：指错按钮比不指更坏——学生会按错，实验做废还以为是软件问题。
- **修复方向**：锚点记录采集时的 DPI/scale，匹配前按当前 DPI 预缩放；尺度集是否扩到 0.67 / 2.0 要拿数据说话，不能凭感觉加。

### P2 · 主题实时切换（浅色 ↔ 深色）

- **现象**：Windows 深色模式或软件自带深色主题会把界面反色，NCC 相关系数变负。
- **现在的行为**：实测 `themeInvert` 会 `coarse-no-candidate` 降级——**这是正确行为**，因为指错更糟。
- **没验的部分**：切换瞬间（不等重绘完成）截图、只改标题栏不改内容区、软件内主题与系统主题不一致。
- **具体怎么测**：同一锚点在浅色下命中后，切深色，再 `anchor_locate`；再切回浅色确认恢复。
- **通过标准**：不误指；若降级率 100%，就把它记成已知限制，**不要为了"看起来能用"去做反色匹配**——反色匹配会把深色按钮误配到浅色空白，误报率反而上升。

### P3 · 双屏 / 混合 DPI（150% + 100%，副屏在主屏左侧 → 负坐标）

- **现象**：窗口拖到副屏后，`GetWindowRect` 的 X 可能是负数；UIA 的 `rect` 是屏幕绝对坐标，`rel` 才是相对整窗。
- **现在的设计**：`guide` / `click` / `screenshot` 一律用**整窗相对坐标**（0.14.3 起的统一基准），这一条从结构上避开了虚拟桌面原点问题。`/inspect` 同时返回 `rect` 和 `rel`，合并 page-map 时必须用 `rel`。
- **没验的部分**：
  - 副屏截图：`PrintWindow` 理论上与屏幕位置无关；但 DWM 窗口失败时会退回 `CopyFromScreen(rect.Left, rect.Top, ...)`，这条路径直接用屏幕坐标，**多屏 + 负坐标下没验过**。
  - 桌宠避让：`Screen.FromRectangle` / `Screen.FromHandle` 在混合 DPI 下的取屏结果。
  - 点击安全闸：`PointBelongsTo` 在负坐标下会不会误拒或误放。
- **具体怎么测**：把目标窗口拖到副屏（最好让副屏在主屏左侧，制造负坐标）→ 截图 → 指引一个控件 → 点一次（`confirm:false` 预演，不真点）→ 看三件事是否都对。
- **通过标准**：副屏窗口截图内容正确（不是黑图、不是主屏内容）、指引坐标正确、点击闸不误判、桌宠不跑到主屏去避让。
- **风险点**：WinForms 面板/气泡在副屏可能被裁切（PerMonitorV2 只保证进程感知，不保证控件重排）。
- **当前受阻**：本机只有一块 2560×1600 内置屏。需要接 HDMI 显示器/电视，或换一台有双屏的机器。

### P5 · 高 DPI 下面板与气泡布局

- **现象**：面板和气泡的尺寸是写死的像素值，150% 下可能字号不变、按钮被裁、气泡超出屏幕。
- **已有证据**：150% 下单屏跑过，没做系统性测量。
- **具体怎么测**：和 P1 共用一次改缩放——每档 DPI 下打开面板截图，量面板矩形与屏幕工作区、量按钮间距、看文字是否截断。
- **通过标准**：100 / 125 / 150 / 200% 四档，面板完整可见、按钮不重叠、气泡不越界。
- **修复方向**：按 `DeviceDpi` 缩放尺寸常量。改 WPF 成本太高，不做。

### P4 · 首次编译验证（最后做）

- **现象**：桌宠首次运行要编译 `overlay/LabPet.cs`，结果缓存到 DSH home。`lib/overlay.mjs` 里有两条编译路径：装了 Visual Studio 的机器走 Roslyn，没装的退回 `%WINDIR%\Microsoft.NET\Framework64\v4.0.30319` 的旧编译器（**只支持 C# 5**）。
- **已有证据**：本机 + 干净 `DSH_HOME` 编译成功；`package.json` 已排除 `overlay/*.exe`，倒逼用户机器首次编译。
- **2026-11-10 新发现（真缺口）**：本机装了 VS 2022 Community，`findRoslynCsc()` 一直命中 Roslyn，**旧编译器回退路径一次都没跑过**。而学生机器大多没装 VS，走的正是这条没验过的路。

#### P4a · 零下载（**已验，2026-11-11，0.15.18**）

- 强制走 `%WINDIR%\Microsoft.NET\Framework64\v4.0.30319` 的编译器编译一次 `LabPet.cs`，确认它仍是 C# 5 兼容、能编出可运行的 exe。
- 做法：加环境变量 `DSH_LAB_FORCE_FRAMEWORK_CSC=1`，只影响"选哪条编译器"，不改编译参数；单测覆盖"两条路都能选到"。
- 产出：两份 `build.log`（Roslyn 一次、旧编译器一次）+ 各自编出的 exe 能启动。
- **结果**：两条路径均 `exit=true`、启动成功、`/status` 返回 `state: swim`；旧编译器 991 ms / 84992 B，Roslyn 1379 ms / 82432 B。证据 `temp/p4a/`。
